1. MODELO DE RAMAS ADOPTADO
----------------------------------------------------------------
Flujo estricto, forward-only, solo por Pull Request:

    feature/* ──PR──▶ dev ──PR──▶ staging ──PR──▶ main

  - main     : producción. Solo recibe releases.
  - staging  : ensayo de release; últimos ajustes antes de prod.
  - dev      : integración de features (rama por defecto del repo).
  - feature/*: efímeras, una por cambio; nacen de dev y vuelven a dev.

Estrategia de merge:
  - feature -> dev     : SQUASH (un commit limpio por feature).
  - dev -> staging     : MERGE COMMIT (preserva el límite de promoción).
  - staging -> main    : MERGE COMMIT + TAG de release (vX.Y.Z).

Reglas:
  - Promoción de una sola vía; nunca hacia atrás.
  - Nunca commits directos a dev / staging / main (solo vía PR).
  - Los hotfixes NO tienen ruta especial: se hacen en feature/*
    desde dev y se promueven por el pipeline normal.

6. RECORDATORIO DE FLUJO DE TRABAJO DIARIO
----------------------------------------------------------------
  # empezar una feature
  git checkout dev && git pull
  git checkout -b feature/<desc>
  # ...trabajar y commitear...
  git push -u origin feature/<desc>
  # abrir PR hacia dev (squash al mergear)

  # promover (cuando dev esté listo)
  PR dev -> staging   (merge commit)
  PR staging -> main  (merge commit) + tag vX.Y.Z
